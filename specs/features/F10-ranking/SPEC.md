# F10 — Ranking (`internal/pick`)

Depends on: F02, F09

## 1. Purpose

`internal/pick` is the pure, deterministic ranking layer of the catalog pipeline: it takes scored model rows (`catalog.ScoreRow`, produced by F09's scores CSV) and a ranking profile, and returns an ordered recommendation with alternatives, a structured list of excluded candidates with machine-readable reasons, and the availability-filter outcome. It has **no CLI surface** — the `which-model pick` command (F22 `NewPickCmd`) and its JSON output are separate concerns. It imports only `internal/catalog` types, `internal/decimal` (F02), and `internal/routing`-free plain types; it never touches the network, the filesystem, or `internal/usage`.

## 2. Behaviour

1. **Profile table.** `internal/pick` ships exactly the 11 built-in profiles of `rank_models.py:124-171`, reproduced verbatim from `docs/plan/annex-b-catalog-port.md §5.1` (simple_implementation 80/20; simple_action_execution 65/35; balanced_implementation 70/30; complex_implementation 60/40; ui_ux 60/40; complex_action_execution 60/40; financial_work 60/40; research 60/40; planning 60/40; orchestration 60/40; review 65/35). The `Profile` struct itself is the **global** type from `specs/global/CONTRACTS.md §4.3` (string-keyed `Tier1Weights map[string]decimal.Decimal`), never redefined. `Tier1Axis` constants (`AxisIntelligence="intelligence"`, `AxisCost="cost"`, `AxisSpeed="speed"`), `Tier1ScoreColumn`, and `CategoryNames` (12 names, fixed order) are F10-owned declarations copied from `annex-b §5.1`.
2. **Built-in profile validity is enforced at construction.** `mustProfile` runs `ValidateProfile` and panics on failure, mirroring Python's import-time crash for an invalid built-in (`annex-b §5.1`). A package-level `var Profiles` initializer that panics is the correct Go equivalent; a `TestBuiltinProfilesAreValid` test additionally asserts every entry passes `ValidateProfile` so the failure mode is a clean test failure, not a startup crash.
3. **`ValidateProfile` rules** are those of `rank_models.py:80-103` (`annex-b §5.2`), with the exact six error messages: share sign/positivity, shares sum to exactly 100, tier-1 keys exactly `{intelligence, cost, speed}` (missing/unknown named in one message), tier-1 weight bounds `0 < w <= 5`, unknown tier-2 category names (sorted), tier-2 weight bounds `0 < w <= 5`. A tier-2 category is omitted from the map to skip it; a present key with weight 0 is an error.
4. **Tier-1 scoring and exclusion.** For each row, the three axis scores are read from `row.Tier1` via `Tier1ScoreColumn` (`annex-b §5.3` step 1-2). A row missing any of the three is **excluded with reason `"missing_tier1:<comma-joined-missing-axis-names>"`** in the fixed axis order `intelligence, cost, speed` — no imputation, hard cut, and this exclusion happens **before** any availability filtering. Otherwise `tier1Score = Σ(v·w) / Σw` over exactly the three axes (a weighted mean independent of `Tier1Share`), computed with F02 `decimal.WeightedMean` (`specs/global/CONTRACTS.md §2.3` pin; weights renormalize by construction).
5. **Tier-2 scoring and missing-data rules.** For each category with a positive weight in `profile.Tier2Weights`, read the row's category score; a blank category appends to `missingOptional` (and later a warning) but never excludes the row. If at least one category has data: `tier2Score = Σ(v·w)/Σw` **renormalized over only the categories with data** (missing categories excluded from both numerator and denominator, never zero-imputed) — verified against the real pipeline: `(5·91 + 2·100)/7 = 655/7 = 93.5714285714285714285714285714285714` (`docs/plan/research/model-data-pipeline-spec.md §6.3` step 5). If NO category has data and `Tier2Weights` is non-empty: `tier2Score = nil` with warning `"no optional task-category scores available; Tier 1 score used"`.
6. **Combination asymmetry — preserve exactly** (`annex-b §5.3` step 7, `pipeline-spec §6.3` closing note). With tier-2 data: `tier1Contribution = tier1Score·Tier1Share/100`, `tier2Contribution = tier2Score·Tier2Share/100`, `total = sum`. Without tier-2 data: `total = tier1Score` (the **raw, un-shared** tier-1 score), `tier1Contribution = tier1Score`, `tier2Contribution = 0`. A no-tier-2 row can therefore outrank an otherwise-identical row that does have tier-2 data; this is Python's intentional "don't punish missing data" design, not a bug, and the port must preserve it including in fixtures that assert relative ranking order.
7. **Warnings** are emitted verbatim (`annex-b §5.6`): `"missing optional category scores: <names>"` when one or more (but not all) requested tier-2 categories are blank; `"no optional task-category scores available; Tier 1 score used"` when all are blank (only when `Tier2Weights` is non-empty). Both warnings fire together when every requested category is blank — this is the real, observed behavior of the Python ranker and is pinned by a test.
8. **Warning/category iteration order is deterministic by decision.** Go maps have no insertion order, so `Tier2Weights` is iterated in **`CategoryNames` order** (F10 decision D2). This matches Python's dict-insertion order for `balanced_implementation` (the order pinned by real pipeline output `"missing optional category scores: instruction_following, agentic_tools"`) and is a documented, order-only deviation from Python's literal declaration order for profiles whose tier-2 literal order differs (simple_action_execution, complex_implementation, ui_ux, complex_action_execution, financial_work, research, review). Arithmetic is order-independent; only warning strings and JSON key order are affected.
9. **Tie-breaking** is the exact 7-key tuple of `rank_models.py:439-449` (`annex-b §5.4`), in order: total DESC, tier-1 intelligence DESC, tier-2 contribution DESC, tier-1 speed DESC, tier-1 cost DESC, `model` case-folded ASC, `reasoning` case-folded ASC. Implemented as a comparator with early return on the first non-equal key — never a composite key or a stable-sort fallback. Verified: two identical rows "Beta"/"Alpha" rank Alpha first.
10. **Availability filter — signature only, applied last** (`annex-b §5.5`). `Rank(rows, profile, available)` takes `available []Identity`; `nil` means no filter. Every fully-scored row whose `(model, reasoning)` is not an **exact tuple member** of the available set is excluded with reason `"not_live_available"`. Applied after all scoring, so `missing_tier1` (data completeness) is structurally distinct from `not_live_available` (runtime availability) even for a row failing both. There is no fuzzy/substring/case-insensitive matching and no second cleaning pass on the model name.
11. **Two distinct terminal errors** (`annex-b §5.5` step 3, strings MUST stay distinct): with an availability filter and zero survivors → `"no candidates remain after live model-and-effort availability and Tier 1 filtering"`; without → `"no candidates contain all mandatory Tier 1 scores"`. Both are `pick.NoCandidatesError` (F22 maps both to exit 3 per `specs/global/SPEC.md §5`), but the message distinguishes "catalog has no usable data" from "availability is too narrow".
12. **Excluded rows are sorted** case-folded by `(model, reasoning)` ascending, stably (`rank_models.py` `sorted(excluded, ...)`; `sort.SliceStable`), preserving exclusion-application order for ties.
13. **Result shape.** `Result{Profile, Recommendation, Alternatives, Excluded, CandidateCount, AvailabilityFilterApplied}` mirrors the Python output object (`annex-b §5.8`): `recommendation` = first ranked survivor, `alternatives` = every other ranked survivor (top-N truncation is CLI scope — F22's `--top`; `internal/pick` returns all survivors). `candidate_count` = number of candidates surviving both filters (real verified: 1 with a restrictive availability set), `availability_filter_applied` = whether a filter was supplied.
14. **Decimal serialization.** JSON output uses `decimal.Decimal.MarshalJSON` (text-based, precision-preserving); the internal `_tie_*` sort keys are never serialized (`annex-b §5.8`).
15. **`ProfileFromJSON`** ports `rank_models.py` `profile_from_json` (flat `tier1_weights`/`tier2_weights`/`tier1_share`/`tier2_share` and nested `tier1:{share,weights|axis...}` / `tier2:{share,weights|category...}` forms; defaults share 100/0), with the exact error messages ("weights JSON is invalid: ...", "weights JSON must be an object", "weights JSON tier1/tier2 weights must be objects", `{tier} weight names must be non-blank strings`, `{tier} weight {name} must be numeric/finite/between 0 and 5`). The produced profile is validated by `ValidateProfile` before return.
16. **`ParseAvailability`** ports `rank_models.py` `_availability_values`/`_identity`/`parse_availability` semantics on bytes: JSON array whose elements are a plain string (parsed by the separator rule), an object `{"model","reasoning"}`, or a `[model, reasoning]` pair; plain-text fallback with blank/`#` lines skipped and an optional case/space-insensitive header line (`model,reasoning` or `model|reasoning`) skipped; separators tried in priority order `"|"`, `"::"`, `","`, `"/"` with a **last-occurrence** split; both halves non-blank after trimming or error. Duplicates collapse (set semantics).
17. **Input preconditions.** `Rank` consumes already-validated rows: duplicate `(model, reasoning)` identities and out-of-range score cells are rejected at parse time by F09 `score.ParseScoresCSV` (`specs/features/F09-scoring/CONTRACTS.md`), never silently merged (`annex-b §3.2` row 4). `Rank` documents this precondition and does not re-validate row content.
18. **No routing/usage dependency.** The availability set is a plain `[]Identity`; the live-availability join from `internal/routing` (F18+) is explicitly **out of scope** for F10 (graph row F10 → F02, F09; `specs/DEPENDENCY-GRAPH.md`). The F10 hook is the signature `Rank(rows, profile, available []Identity)` — a later feature wires routing output into `available`.

## 3. Error behaviour

- Validation and parse failures return `*pick.RankingError` with the verbatim messages above (F22 maps to exit 2).
- The two no-viable-candidate conditions return `*pick.NoCandidatesError` with the distinct verbatim messages (F22 maps to exit 3).
- Errors never contain score data or profile contents beyond the message text; no credentials are involved anywhere in this package.

## 4. Decisions

| Decision | Value | Rationale |
|---|---|---|
| D1 Profile type source | Global `Profile` from `specs/global/CONTRACTS.md §4.3` (string-keyed maps); `Tier1Axis`/`Tier1ScoreColumn`/`CategoryNames` are F10-owned copies of `annex-b §5.1` | Global types are canonical; the annex's typed-enum variant is superseded by the global contract (README: spec wins) |
| D2 Tier-2 iteration order | `CategoryNames` order, not map order | Go maps are unordered; CategoryNames is the canonical fixed order and matches Python's insertion order for balanced_implementation, the order real pipeline output pins |
| D3 top-N location | `internal/pick` returns all ranked survivors; `--top` truncation is F22 CLI scope | Keeps `internal/pick` CLI-free per assignment; Python's `top_n` default-1 and `"top-n must be positive"` move to the command layer |
| D4 No-tier-2 asymmetry | `total = tier1Score` unscaled when tier-2 evidence is absent | Python's intentional "don't punish missing data" design (`annex-b §5.3` step 7); MUST be preserved, tested with a fixture asserting the relative order |
| D5 Availability is exact tuple membership | No fuzzy matching, no cleaning pass | `rank_models.py` `available={(...)}` set semantics (`annex-b §5.7`) |
| D6 Both warnings fire when all tier-2 categories are blank | Observed real behavior (only.csv run, simple_action_execution): `"missing optional category scores: ..."` AND `"no optional task-category scores available; Tier 1 score used"` | The Python code appends both unconditionally (`rank_models.py:400-408`); `annex-b §5.6` wording is ambiguous but the behavior is pinned by test |
| D7 Excluded-row sort | casefold `(model, reasoning)` ascending, stable | Matches `sorted(excluded, ...)` (stable) in `rank_models.py:480` |

## 5. Out of scope

- CLI, flags, `--json`/`--pretty` output, `--top`, exit-code mapping (F22 `NewPickCmd`; `specs/global/SPEC.md §5`).
- Routing/usage join: sourcing live availability, allowance windows, provider routing (F18 routing; F23+ commands).
- Scores-CSV parsing and duplicate/range validation of input rows (F09 `score.ParseScoresCSV`).
- Profile persistence, user-defined profile files, `--weights-json` flag parsing (F22; F10 exposes `ProfileFromJSON`).

## Review correction — #185: explicit category vocabulary

`ValidateProfileWithCategories(profile, categories)` applies all six validation rules with the supplied list as rule 5's exact category vocabulary. `RankWithCategories(rows, profile, available, categories)` uses that validator and the existing scoring, exclusion, availability, and sorting pipeline. The existing `ValidateProfile` and `Rank` delegate with `CategoryNames`, preserving CLI behavior and avoiding global mutation. Desktop callers may explicitly include configured custom group slugs. Unknown names still fail; shares and mandatory core-axis rules do not change.
