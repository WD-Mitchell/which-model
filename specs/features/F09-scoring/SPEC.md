# F09 — Scoring (`internal/catalog/score`)

Depends on: F02, F06, F07

## 1. Purpose

`internal/catalog/score` is the deterministic, offline scoring engine of the catalog pipeline: it turns the raw model-data CSV (F08 collectors / F23 refresh) plus the benchmarks catalog TOML into the scores CSV that `internal/pick` (F10) consumes. It owns the dual-column output schema (absolute metrics carried through, relative `_score` columns normalized to 0-100), the 12 task-category composite formulas, the planning-capability formula, and the provenance header of the scores artifact. It is pure computation — no network, no filesystem, no HTTP — and MUST NOT import `internal/catalog/fetch/**` (any package) or `internal/usage`/`internal/routing`; it imports only `internal/catalog` types, `internal/decimal` (F02), `internal/catalog/identity` (F07), `internal/catalog/csvstore` (F06), and stdlib (`specs/global/CONTRACTS.md §8`).

## 2. Behaviour

1. **Inputs and signature.** `Derive(rawCSV []byte, benchmarksTOML []byte, normalizer Normalizer, aggregator Aggregator) ([]byte, error)` is the single public entry point (`docs/plan/annex-b-catalog-port.md §3.1`): pure bytes-in/bytes-out, offline, deterministic. `Normalizer`/`Aggregator` are the global interfaces from `specs/global/CONTRACTS.md §2.2` (verbatim, never redefined); F09 exports `DefaultNormalizer()` (`MinMaxLinear`) and `DefaultAggregator()` (`WeightedArithmeticMean`), plus `ResolveNormalizer(name)`/`ResolveAggregator(name)` returning typed errors for unknown names (F23 maps to exit 2).
2. **Normalizer semantics — MinMaxLinear** (`docs/plan/research/model-data-pipeline-spec.md §3.1`, `generate_scores.py normalized_score`). For one metric, with observed minimum `min` and maximum `max` over the **eligible rows** (see 5): higher-is-better metrics use `score = round(((v - min) / (max - min)) * 100, 0)`; the three latency/cost metrics — `time_per_intelligence_index_task_seconds`, `cost_per_intelligence_index_task_usd`, `median_end_to_end_response_time_seconds` — are **lower-is-better** and use `score = round(((max - v) / (max - min)) * 100, 0)` (CORE_METRICS direction flags in `generate_scores.py:29-35`; benchmark metrics are all higher-is-better). If `max == min` (degenerate range) the metric is **optional** and renders a blank column when it has no published values; otherwise the score is `decimal.Round(0)` — ROUND_HALF_UP (F02 pin; `specs/global/CONTRACTS.md §2.3`). Min/max are computed with decimal arithmetic on the raw CSV values (never float64); negative raw values for the three latency/cost metrics are a hard parse error before normalization (`generate_scores.py:117-121`).
3. **Aggregator semantics — WeightedArithmeticMean** (`pipeline-spec §4.1`, `generate_scores.py weighted_arithmetic_mean`). For a composite, `score = round(Σ(vᵢ·wᵢ) / Σwᵢ, 0)` where weights are the fixed category weights of `docs/plan/annex-b-catalog-port.md §5.1` and only **populated** evidence participates: blank values are excluded from BOTH numerator and denominator — never zero-imputed (`generate_scores.py:229-237`). If the denominator is empty (no populated evidence), the composite is blank. This is Decision D1.
4. **Score quantum.** Every score cell (relative `_score` columns) is an integer `0-100` after `Round(0)` ROUND_HALF_UP — never `RoundBank`, never fractional (`pipeline-spec §4.1`; Decision D2). Verified against the real pipeline: intelligence 55.6 → 63, cost 0.37 → 93, time 15 → 100, coding 76.3 → 90, agentic 47.9 → 61 (values from `generate_scores.py` run on `available-model-data-export/available_model_raw_values.csv` rows, `docs/plan/research/model-data-pipeline-spec.md §1.3`).
5. **Eligibility for relative normalization.** A row is **eligible** iff all three Tier-1 metrics are present: `intelligence_index`, `median_end_to_end_response_time_seconds`, `cost_per_intelligence_index_task_usd` (`generate_scores.py:185-192`, `pipeline-spec §2.2` REQUIRED_TIER1). **Ineligible rows are excluded from the output entirely** — the Python generator writes only `eligible_rows` (`generate_scores.py:391`), and the Go port preserves this exactly (Decision D9); ineligible rows contribute nothing, not even absolute columns. Zero eligible rows is a hard error: `input contains no rows with all mandatory Tier 1 metrics: intelligence_index, median_end_to_end_response_time_seconds, cost_per_intelligence_index_task_usd` (`generate_scores.py:193`). A raw CSV with zero data rows at all fails earlier with `input contains no data rows` (`generate_scores.py:205`).
6. **Per-metric optionality** (`pipeline-spec §2.2`, `generate_scores.py:89-93`): `time`, `coding`, `agentic` are OPTIONAL_METRICS — a degenerate range (max == min over eligible rows) or zero published values renders that metric's `_score` column blank while still emitting the absolute column. `intelligence` is mandatory: degenerate → hard error `intelligence_index has a degenerate range (<minimum>)` (`generate_scores.py:146-148`). All metrics are nullable per-row: a blank absolute value yields a blank `_score` (no imputation; `pipeline-spec §2.2` NULLABLE).
7. **Raw CSV validation before any scoring** (`generate_scores.py` `read_rows`, `pipeline-spec §2.1`): 8 core columns in the fixed RawCoreColumns order, then dynamic benchmark columns (`benchmark:<name>`); a blank cell in a core column is an error `row <n>: <column> must not be blank`; non-numeric → `row <n>: <column> must be numeric, got '<value>'`; non-finite → `... must be finite, got '<value>'`; negative for the three latency/cost metrics → `... must not be negative, got '<value>'`; wrong arity → `row <n>: too many values` / `row <n>: too few values`; core headers wrong → `unexpected core columns: expected <joined>, got <joined>`; benchmark columns invalid or duplicated → `invalid or duplicate dynamic benchmark columns`; empty file → `input contains no data rows`. Message format is Python-verbatim and **row numbers start at 2** (row 1 is the header; `csv.DictReader` `enumerate(start=2)` in `generate_scores.py:169`). Message format is Python-verbatim (`pipeline-spec §2.1`, `generate_scores.py:95-125`).
8. **Raw duplicate-identity merge** (Decision D8, `generate_scores.py _merge_input_rows`): after parsing, rows whose identities collide under cleaning are merged **in input order, first-wins**: `CleanModelName` on `model` (blank-after-clean → `model name is blank after removing annotations`), `CollapseReasoning` (`default`→`high`) on `reasoning`; the first row's core cells win (later rows only fill blanks), benchmark cells take the **max** of colliding rows. This is a defensive port for dated/annotated snapshots and applies inside Derive only — the strict `csvstore.ErrDuplicateIdentity` rejection in `csvstore.ValidateRawRows` (F06) still governs F23's refresh path on freshly collected data.
8. **12 category composites** (`pipeline-spec §5.1` `CATEGORY_GROUPS` + `generate_scores.py _category_score`): the fixed 11 groups (reasoning, knowledge, research, instruction_following, software_engineering, ui_visual, agentic_tools, finance, evidence_capture, security, data_ml) with the **per-column minimum-evidence gate** of `generate_scores.py:66-81` — `security_score` needs 1 populated evidence, every other category needs 2 (`CATEGORY_MINIMUM_EVIDENCE`, verified by the real pipeline: `software_engineering` = 50 for both Claude Opus 5 and GPT-5.6 Sol from exactly two populated evidences (100+0)/2). Formula per category: unweighted mean (`_rounded_average`, sum/len, ROUND_HALF_UP) of the populated evidence scores; blank when evidence count < minimum. Evidence resolution is **two-layer dedup** (Decision D3, `generate_scores.py _source_scores` + `_category_score`): layer (a) at the source level, iterating **raw CSV header order** — the two AA index score columns first seed canonical keys `Artificial Analysis Coding Index` / `Artificial Analysis Coding Agent Index` (via F07 `BenchmarkKey`), then every `benchmark:<name>` column `setdefault`s its key, so the first CSV column whose key collides wins (AA-index-preferred over models.dev, `annex-b §4.5`); layer (b) at the group level, iterating the **benchmarks.toml group list order** with a `seen` key set — the first group member whose key collides wins. Both layers reproduced the real "65" case (`pipeline-spec §5.2`): `Finance Agent=50` beats `FinanceAgent=100`, `GDPval=80` beats `GDPval-AA=0`, composite `(50+80)/2=65`.
9. **Planning capability** (`generate_scores.py planning_capability_score`, `pipeline-spec §5.2`): `planning_capability = round(0.4·reasoning + 0.3·knowledge + 0.2·agentic_tools + 0.1·research, 0)`; ANY of the four inputs blank → composite blank (verified: the "80" case where missing `research` blanks the composite). Implemented as a WeightedArithmeticMean with weights {reasoning:40, knowledge:30, agentic_tools:20, research:10}/100 — blank-input exclusion is exactly the D1 rule, so no special case code beyond the weight set.
10. **Dual-column output schema** (`annex-b §4.0a`, Decision D4): scores CSV rows carry the identity columns (`model`, `reasoning`), then for each of the 6 core metrics an interleaved pair in **RawCoreColumns order** — `intelligence_index`, `time_per_intelligence_index_task_seconds`, `cost_per_intelligence_index_task_usd`, `median_end_to_end_response_time_seconds`, `artificial_analysis_coding_index`, `artificial_analysis_agentic_index` (each: absolute `<metric>` raw value verbatim, blank when absent, then `<metric>_score` normalized integer or blank) — then the 12 category `_score` columns in CATEGORY_SCORE_COLUMNS order (reasoning, knowledge, research, planning_capability, instruction_following, software_engineering, ui_visual, agentic_tools, finance, evidence_capture, security, data_ml), then per-benchmark pairs in the raw CSV's dynamic-column order: `benchmark:<name>` (absolute) and `benchmark:<name>_score` (relative). Relative benchmark scores use the same min-max normalization over the eligible-row set (higher-is-better), with the degenerate/optional split of 6: a benchmark column with a degenerate range is optional and renders blank (verified: singleton benchmark columns render blank, e.g. SWE-Bench Verified for the golden fixture). `internal/pick` reads only the `_score` columns, so the old single-column layout of the Python CSV is fully superseded (the Python output also replaced the benchmark absolute value with its score; the Go schema keeps both).
11. **Benchmark config parsing.** `ParseBenchmarkConfig(data []byte) (*BenchmarkConfig, error)` parses the benchmarks catalog TOML (strict: unknown keys are errors, mirroring `generate_scores.py:35-40` TOMLDecodeError handling); `BenchmarkConfig` carries `CanonicalBenchmarks` (name → aliases) and category `Evidence` groups in file order (annex-b §3.1). `identity.BenchmarkKey`/`BenchmarkAliases` (F07) canonicalize raw CSV benchmark column names and evidence names; unknown evidence names are a hard error.
12. **Provenance header** (`annex-b §6.2a`; Decision D5): the output starts with exactly one line `# which-model-scores-provenance raw_sha256=<64-hex> normalizer=<name> aggregator=<name>` where `<hex>` is `csvstore.ProvenanceHash(rawCSV)` and the names are the resolved normalizer/aggregator names (`minmax-linear`, `weighted-arithmetic-mean`); then the CSV rows. `Derive` returns these complete bytes; **F23 owns the write** (`csvstore.Backup(path, DefaultBackupKeep)` then `csvstore.WriteAtomicBytes(path, derived)` or the re-render fallback — F06 contract, see `specs/features/F06-*/CONTRACTS.md`). `ParseScoresCSV(data []byte) ([]catalog.ScoreRow, error)` validates that a leading `#` line, when present, has the `ProvenancePrefix` shape per F06 rules (`ErrMalformedCSV` on a second `#` line or a malformed `raw_sha256=` token) but does not expose provenance — F23 reads it via `csvstore.Read`/`StaleCheck`.
13. **Determinism** (Decision D6): all iteration over raw CSV columns and benchmark columns follows **CSV header order**; all map iteration over unordered Go maps is forbidden in output-producing paths (the `_source_scores` dedup iterates header order — the Go map is only a lookup); category evidence iterates benchmarks.toml group-list order. Same inputs + same config ⇒ byte-identical output, including the header line.
14. **`ParseScoresCSV` row semantics** (`rank_models.py:359-401` port, `annex-b §3.2`): scores CSV must contain the required `_score` columns (error `score CSV is missing required columns: <sorted>`), every row must have a non-blank `model` and `reasoning` (`score CSV row <n> has a blank model/reasoning identity`), no extra cells (`score CSV row <n> has extra cells`), duplicate identities are rejected (`score CSV has duplicate identity: <model> / <reasoning>` — rejection lives HERE, not in F10), score cells must be within 0-100 (`score CSV row <n> <column> must be between 0 and 100`), and zero rows is an error (`score CSV contains no model rows`). All `_score` columns parse to integers (relative columns are emitted integer by construction).
15. **`ScoreRow` mapping** (Decision D7): `Tier1` keyed by the 6 `<metric>_score` column names, `Categories` keyed by plain category names, `Benchmarks` keyed by benchmark name — exactly the keys `internal/pick` (F10) reads via `Tier1ScoreColumn` and `CategoryNames`. Blank cells are absent keys.
16. **Typed errors.** `*score.Error` carries `Code` (`ErrInvalidRaw`, `ErrInvalidBenchmarkConfig`, `ErrInvalidScoresCSV`) + the verbatim message; F23 maps to exit 1 (data error, `specs/global/SPEC.md §5`). `ResolveNormalizer`/`ResolveAggregator` return `*score.Error` with `ErrUnknownNormalizer`/`ErrUnknownAggregator` (exit 2 via F23).
17. **Canary security note**: the scores pipeline contains no credentials; the provenance header embeds only a SHA-256 digest and names. No canary-token test is required here (no usage data); the requirement applies to F21/F23 usage-touching paths (global SPEC §6).

## 3. Error behaviour

All messages are Python-verbatim (`generate_scores.py`, `rank_models.py`); the complete table with exact strings is in `specs/features/F09-scoring/CONTRACTS.md §1.3`. Error precedence: raw CSV structural errors → benchmark config errors → eligibility/normalization errors → derivation. `ParseScoresCSV` failures are `ErrInvalidScoresCSV`. Unknown normalizer/aggregator names are configuration errors (exit 2); all data errors are exit 1.

## 4. Decisions

| Decision | Value | Rationale |
|---|---|---|
| D1 Missing-value handling in weighted mean | Blank evidence excluded from both numerator and denominator; no imputation; empty denominator → blank composite | `generate_scores.py` `_category_score`/`_rounded_average` verbatim; matches real pipeline output (Kimi K2.7 Code row: missing time/coding yield blank `_score` cells, not 0) |
| D2 Score quantum | Integer 0-100, `decimal.Round(0)` ROUND_HALF_UP, never RoundBank | F02 pin (`specs/global/CONTRACTS.md §2.3`); Python `quantize(ROUND_HALF_UP)` is the same rounding; verified identical on real values (55.6 → 63, 0.37 → 93, 15 → 100, 76.3 → 90, 47.9 → 61) |
| D3 Evidence dedup | Two layers: (a) source-level first-wins in raw CSV header order with AA-index columns seeding first; (b) group-level first-wins in benchmarks.toml group list order | `generate_scores.py` `_source_scores` (`setdefault` in output-column order) + `_category_score` (`seen` in group order); reproduces the real "65" case (`pipeline-spec §5.2`); deterministic |
| D4 Dual-column schema | Absolute `<metric>`/`benchmark:<name>` verbatim + relative `_score` 0-100, interleaved pairs; category columns are `_score`-only | `annex-b §4.0a`; F10 reads only `_score`; the Python CSV's single-column layout (which replaces the absolute benchmark value with its score) is superseded — Go golden fixtures are hand-built to the new schema |
| D5 Provenance | Single `# which-model-scores-provenance` line, `raw_sha256` required + `normalizer`/`aggregator` optional; Derive returns bytes; F23 writes | `annex-b §6.2a` + F06 `Provenance`/`ProvenancePrefix` contract; keeps Derive pure |
| D6 Determinism | CSV-header-order iteration everywhere; no Go-map-order output | Same input ⇒ byte-identical output; Go maps are unordered |
| D7 ScoreRow keying | Tier1 keyed by `_score` column names, Categories by plain names, Benchmarks by name | Matches F10's read keys (`Tier1ScoreColumn`, `CategoryNames`) — one seam, two sides |
| D8 Raw duplicate identities in Derive | Merged: first-wins fill-in for core cells, max for benchmark cells, after `CleanModelName` + `default`→`high` collapse; `csvstore.ValidateRawRows` still rejects duplicates for F23's refresh path | `_merge_input_rows` port (`generate_scores.py:136-162`); the two contracts serve different inputs (defensive merge for legacy snapshots vs strict validation of fresh collector output) |
| D9 Ineligible rows | Dropped from the scores CSV entirely (no absolute-only rows) | Python writes only `eligible_rows` (`generate_scores.py:391`); matches the golden fixture (5 raw rows → 3 scores rows) |

## 5. Out of scope

- Fetching raw data (F08 collectors), refresh orchestration, providers.toml, cache, `catalog providers` (F23 `internal/catalog` commands).
- Writing the scores file: F23 owns `csvstore.Backup` + `WriteAtomicBytes` (F06 contract); Derive returns bytes only.
- Ranking, profiles, tie-break, availability (F10 `internal/pick`).
- Usage-aware scoring, allowances, `nousage` build tag (F21; F09 compiles under `-tags nousage` because it has no usage dependency — `specs/DEPENDENCY-GRAPH.md` row F09).
- Config-file reading (`[scoring]` keys are read by F23 via F01 `UnmarshalKey`; F09 exports `ResolveNormalizer`/`ResolveAggregator` for that).
